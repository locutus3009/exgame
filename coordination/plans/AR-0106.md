# AR-0106 plan — Fatal semantics: size and count fatal slots from the trace

Milestone: [M1](../milestones/M1.md). Task: [AR-0106](../tasks/AR-0106.md).

## Scope

State at 4d5b23c: each invocation has `Fatals { float fatal[20]; }` (crates/newton/build.rs
around 65-67, `FIXME: should be traced.fatal_leaves().len()`); viete writes the traced fatal
operands; row kernels clear fatal[0]; the host check in shaders.rs (around 368-399) scans each
message's span over `fatal[0..n_fatals]` with n_fatals hand-entered per kind (around 451-471) and
fails only that message with `EvalError::Backend`. The commented-out `Term::Fatal` emission in
viete glsl.rs (around 337-340) is dead.

Deliver:
1. The fatal array width is derived from the traced kernels (max over kinds, or per kind), and
   build.rs emits a table of per-kind fatal counts that shaders.rs includes instead of the
   hand-entered numbers. A kernel with more fatal leaves than slots must fail the build.
2. Semantics settled and stated in a doc comment: mark-and-continue per message (outputs still
   written, the message fails). Remove the dead commented-out emission.
3. A test that drives a kernel into a fatal condition (e.g. a joint with coincident anchors or a
   zero-length axis, whichever traces a division guard) and observes `EvalError::Backend` for
   that message only, with its batch-mates succeeding.
